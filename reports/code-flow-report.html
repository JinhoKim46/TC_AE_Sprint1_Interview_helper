What every script does, and how the parts talk to each other

A map of the running system, built by reading the Python code itself: which model plays which role, how one interviewer prompt is assembled, which function calls which, and where every piece of data is born, stored and read.

How to read this

Start with the agents, follow one answer through the prompt journey, then use the call graph to look up any function. Everything with a file:line is clickable.

Facts are generated

Modules, functions, call edges, model roles, schemas, templates and database access come from static analysis of the code (ast), so they match the code at the last build. Calls the analysis couldn't pin to one function are listed as unresolved, never guessed.

The story is checked

The prose around the facts (what an agent is for, the journey steps, the sequence diagrams) is hand-written, but every function it names is checked against the code map on each build. A renamed function shows up as a warning at the top of this page.

Words used here

Agent: one model role, the role string the code passes to the gateway and the call log. Gateway: LLMClient (chat) or DecisionClient (Jev). Edge: one function calls (solid), references (dashed) or injects (dotted) another.

The agents

Every model role in the system: who calls it, which model and prompt it uses, what goes into each message, what comes back and where that ends up. Model ids are the defaults from config.py; the Settings page or .env can change them.
